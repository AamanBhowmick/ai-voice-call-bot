ACS + Custom Webhook — Animated Data Flow

Azure Communication Services · Custom Webhook · AI Voice Agent Architecture

▸ Data Flow Steps
1
PSTN / User Dials ACS Number
Inbound call arrives at your Azure Communication Services phone number.
  • aUser picks up phone and dials the ACS-provisioned PSTN number.
  • bThe PSTN network routes the call to Azure's telephony gateway via SIP.
  • cACS receives the SIP INVITE and registers the call with a unique callId.
  • dCall is in ringing / incoming state — no audio exchanged yet.
2
ACS Emits IncomingCall Event
ACS publishes Microsoft.Communication.IncomingCall to Azure Event Grid.
  • aACS fires a Microsoft.Communication.IncomingCall CloudEvent.
  • bPayload contains: callerId, incomingCallContext, to, and an answer token.
  • cEvent Grid routes the event to all subscribed webhook endpoints.
  • dEvent Grid guarantees at-least-once delivery with automatic exponential-backoff retry.
3
Event Grid POSTs to Custom Webhook
HTTPS POST to your server's /api/incoming-call. Validate the subscription handshake.
  • aEvent Grid sends HTTP POST to https://yourserver.com/api/incoming-call.
  • bFirst registration: Event Grid sends a SubscriptionValidationEvent — echo back the validationCode.
  • cVerify aeg-event-type header and that the payload is a valid CloudEvent.
  • dExtract incomingCallContext — required to answer the call via SDK.
4
Webhook Answers + Attaches Media Stream
Uses Call Automation SDK to answer and stream audio to your WebSocket server.
  • aCall callAutomationClient.answerCall(incomingCallContext, callbackUri) from the ACS SDK.
  • bProvide MediaStreamingOptions with your WebSocket URL and audio format (PCM 16 kHz mono).
  • cACS picks up the call and negotiates the media stream toward your WebSocket server.
  • dA CallConnected event fires to your callback URI once fully established.
5
ACS Opens WebSocket & Streams PCM Audio
Real-time raw audio packets flow from ACS to your WebSocket server.
  • aACS initiates a WebSocket connection to wss://yourserver.com/audio.
  • bAudio is streamed as binary frames: raw PCM 16 kHz, 16-bit, mono, little-endian.
  • cEach frame includes a JSON metadata header (participant ID, timestamp) before the audio bytes.
  • dYour server buffers chunks and feeds them to the STT engine in real time.
6
Audio Forwarded to AI / LLM
Your server pipes audio through STT → LLM pipeline (Gemini, Claude, GPT, etc.).
  • aSTT: PCM chunks sent to Google STT / Azure STT / Deepgram to produce a text transcript.
  • bVoice-activity detection assembles chunks into a complete user utterance.
  • cLLM: Transcript sent to your AI model (Gemini, Claude, GPT-4o) with system prompt + history.
  • dThe LLM streams back a text response token-by-token for the TTS stage.
7
AI Returns Synthesised Speech
The AI processes the query and returns a TTS audio response to the WebSocket server.
  • aTTS: LLM response text sent to Azure Neural TTS / Google TTS / ElevenLabs.
  • bTTS returns synthesised audio in PCM or µ-law format matching ACS's expected codec.
  • cAudio is streamed chunk-by-chunk from TTS to minimise latency (first-byte time).
  • dYour server queues audio chunks ready to send back over the WebSocket.
8
Audio Injected Back into Call
Synthesised speech is streamed through ACS back to the caller. The loop repeats.
  • aYour server sends synthesised PCM frames back to ACS over the same WebSocket.
  • bACS injects the audio stream directly into the active call, playing it to the PSTN caller.
  • cACS continues streaming the caller's audio back — enabling barge-in / interruption detection.
  • dOnce the response finishes, the pipeline resets and awaits the next utterance (Steps 5→8 repeat).

☁ Azure Portal Setup Guide

Step-by-step provisioning for every Azure resource in the architecture above

1
Resource Group
Create a logical container for all your Azure resources
▼
💡What is a Resource Group? Think of it as a project folder on Azure. Every Azure resource you create (ACS, App Service, etc.) lives inside it. When you're done, you can delete the whole group in one click and stop all billing instantly.
1
Go to portal.azure.com. In the top search bar, type Resource groups and click it.
↳ Why: This is your starting point. All other services will be placed here.
2
Click + Create in the top-left.
↳ Why: You can't add anything to a group that doesn't exist yet — this creates the container.
3
Set Subscription → your Azure subscription. Set Resource group name → e.g. rg-voice-bot. Set Region → the data center closest to you, e.g. East US.
↳ Why the name matters: Use a clear name like rg-voice-bot so you immediately know what project it belongs to. Region affects latency — pick what's geographically closest to your users.
4
Click Review + create → then Create. Wait a few seconds for Azure to confirm it's ready.
↳ Why: Azure validates your inputs before provisioning. Once created you'll see it in your portal dashboard.
2
Azure Communication Services (ACS)
Provision the core telephony service + buy a phone number
▼
⚠What is ACS? Azure Communication Services is Microsoft's cloud telephony platform. It receives incoming phone calls, converts them into digital events, and lets your backend code control what happens next — all without managing physical phone infrastructure.
Create ACS Resource
1
In the portal search bar, type Communication Services → click it → click + Create.
↳ Why: This provisions your telephony engine on Azure. Without it you cannot receive or manage phone calls programmatically.
2
Select Resource group → rg-voice-bot. Enter Resource name → e.g. acs-voice-bot. Set Data location → United States (or your region).
↳ Why the data location matters: This is where ACS physically stores call metadata and recordings. Pick the region closest to your users for lowest latency and to satisfy data residency rules.
3
Click Review + create → Create. Once deployed, open the resource → click Keys in the left sidebar → copy the Connection string and save it somewhere safe.
↳ Why the connection string: This is the password your code uses to authenticate with ACS and make SDK calls (e.g. answer a call, stream audio). Never share it publicly.
Buy a Phone Number
4
Inside your ACS resource → click Phone numbers in the left sidebar → + Get → Get a number.
↳ Why: This is the actual dialable phone number your users will call. ACS routes calls to this number into your system.
5
Select your Country. Set Number type → Toll-free (free for callers, you pay per minute) or Geographic (local area number). Under Features → make sure Voice calls is checked.
↳ Why Voice calls must be checked: ACS numbers can be configured for SMS only, voice only, or both. Our bot needs voice — checking this enables the call-receive capability.
6
Click Search → pick any available number → click Buy. Write this number down (e.g. +12025550123) — this is what callers will dial.
↳ Cost note: Phone numbers cost roughly $1–2/month to lease. Inbound calls cost ~$0.004/min on top of that.
3
Deploy Your Webhook Server
Host your custom backend on Azure App Service
▼
ℹWhat is App Service? It's Azure's managed hosting platform for web apps. You upload your Node.js/Python/Java code and Azure keeps it running 24/7 with a public HTTPS URL — no server management needed. This is where your webhook and WebSocket server will live.
Create App Service
1
In the search bar type App Services → click it → + Create → Web App.
↳ Why Web App and not something else: Web App is the simplest option for hosting an HTTP server. Other options (Container Apps, Functions) add complexity you don't need yet.
2
Set Resource group → rg-voice-bot. Set Name → e.g. webhook-voice-bot. Azure turns this into your public URL: webhook-voice-bot.azurewebsites.net.
↳ Why this URL matters: This is the HTTPS address you'll give to Event Grid so it knows where to send incoming call notifications.
3
Set Runtime stack → Node.js 20 LTS (match your code language). Set Region → same region as your ACS resource. Set Pricing plan → B1 Basic.
↳ Why B1 and not Free (F1): The free tier does NOT support WebSockets, which our audio streaming requires. B1 Basic (~$13/month) is the minimum plan that enables WebSocket connections.
4
Click Review + create → Create. Deployment takes 1–2 minutes.
↳ Why wait: Azure is allocating compute resources and setting up the HTTPS certificate for your domain.
Enable WebSockets
5
Open your new App Service → left sidebar → Configuration → General settings tab → find Web sockets → switch it On → click Save.
↳ Why this step exists: WebSocket support is disabled by default even on B1. ACS streams audio to your server over a persistent WebSocket connection — if this toggle is Off, ACS cannot connect and your bot will never receive audio.
Deploy Your Code
6
Left sidebar → Deployment Center → choose GitHub (connects directly to your repo, auto-deploys on every push) or ZIP deploy (manual: zip your project folder and upload it).
↳ Why GitHub is recommended: Every time you push a fix to GitHub, Azure automatically pulls the new code and restarts your app — no manual re-upload needed. Great for iterating quickly.
💡Copy your App Service URL now: https://webhook-voice-bot.azurewebsites.net. You will paste it into Event Grid in the very next phase.
4
Event Grid Subscription
Wire ACS → Event Grid → your webhook endpoint
▼
⚠What is Event Grid? It's Azure's notification router. When ACS receives a call, it publishes an event. Event Grid immediately forwards that event to your webhook URL — like a smart doorbell that rings your phone when a visitor arrives. Without this step your server is deaf to incoming calls.
1
Open your ACS resource (acs-voice-bot) → in the left sidebar click Events.
↳ Why here: The Events section is where ACS exposes its built-in Event Grid integration. This is the correct place to subscribe to call events.
2
Click + Event Subscription at the top.
↳ Why: A subscription tells Event Grid "for this specific event type, deliver it to this specific URL". One ACS resource can have multiple subscriptions forwarding to different destinations.
3
Set Name → incoming-call-subscription. Set Event Schema → Cloud Event Schema v1.0.
↳ Why CloudEvent Schema: It's the modern, standardised event format. The ACS SDK and most tools expect this format — using the older Event Grid Schema may cause parsing errors in your code.
4
Under Filter to Event Types → uncheck all checkboxes → then check only Incoming Call (Microsoft.Communication.IncomingCall).
↳ Why filter: ACS fires many event types (call ended, participant added, etc.). You only care about new incoming calls — filtering prevents your webhook from being flooded with unrelated events.
5
Set Endpoint Type → Web Hook. In the Endpoint field paste: https://webhook-voice-bot.azurewebsites.net/api/incoming-call.
↳ Why this specific path: This is the route your Express server exposes to receive call events. The path /api/incoming-call is just a convention — you can name it anything as long as your code listens on that same path.
6
Click Create. Event Grid immediately sends a one-time SubscriptionValidationEvent POST to your endpoint. Your server must echo back the validationCode within 30 seconds or the subscription will fail.
↳ Why the validation handshake: This is a security measure. Azure needs to confirm you actually own and control that URL before it starts sending real call events to it — otherwise anyone could redirect your events to a malicious server.
ℹOpen App Service → Log stream in a second browser tab before clicking Create so you can watch the validation request arrive in real time.
5
App Settings & Environment Variables
Configure your server with ACS credentials and URLs
▼
ℹWhat are Application Settings? They are environment variables — key/value pairs your running code can read at runtime via process.env.KEY_NAME. Storing credentials here (instead of hardcoding them in your source code) keeps secrets out of GitHub and lets you change them without redeploying code.
1
Open your App Service → left sidebar → Configuration → Application settings tab → click + New application setting and add each row from the table below.
↳ Why here and not in your code file: If you hardcode secrets in code and push to GitHub, anyone who sees your repo can access your Azure account. Environment variables stay server-side and are never exposed in code.
Setting NameValueWhy it's needed

6
Call Automation SDK — Answer & Stream
Core code pattern to answer calls and attach the media stream
▼
ℹWhat does the SDK do? The ACS Call Automation SDK is a library that wraps all the complex ACS REST API calls into simple JavaScript functions. Instead of manually crafting HTTP requests to answer a call, you just call client.answerCall() and the SDK handles the rest.
1
In your project folder run: npm install @azure/communication-call-automation
↳ Why: This downloads the official Microsoft SDK package into your project. Without it you'd have to manually write hundreds of lines of HTTP request code to talk to ACS.
2
Add this route to your Express server. Read the inline comments to understand what each part does:
const { CallAutomationClient } = require('@azure/communication-call-automation'); const client = new CallAutomationClient(process.env.ACS_CONNECTION_STRING); app.post('/api/incoming-call', async (req, res) => { const event = req.body[0]; // ① Subscription validation handshake if (event.eventType === 'Microsoft.EventGrid.SubscriptionValidationEvent') { return res.json({ validationResponse: event.data.validationCode }); } // ② Answer call + attach WebSocket media stream await client.answerCall( event.data.incomingCallContext, process.env.CALLBACK_URI, { mediaStreamingOptions: { transportUrl: process.env.WEBSOCKET_URL, transportType: 'websocket', contentType: 'audio', audioChannelType: 'unmixed', } } ); res.sendStatus(200); });
3
Your /audio WebSocket route receives raw binary audio frames (PCM format) from ACS in real time. Your code should pipe these to a Speech-to-Text service, get a transcript, send it to your LLM, get a response, convert it to audio via TTS, then send the audio bytes back over the same WebSocket socket.
↳ Why PCM and not MP3/WAV: PCM is raw, uncompressed audio — no encoding overhead, minimal CPU on both ends. It's the lowest-latency format for real-time streaming. ACS streams it in 20ms chunks.

Verify the full call flow and where to look when things go wrong

Testing the Full Flow
1
Call your ACS phone number from any phone (use a mobile or landline).
↳ What to expect: The call rings for a moment, then your bot should pick up. If it rings out to voicemail, your server didn't answer — check Step 2.
2
In the Azure Portal, open App Service → Log stream (left sidebar). You should see an HTTP POST arrive at /api/incoming-call with the call event payload.

🔒 Security & Scalability Analysis

Production concerns you must address before going live with thousands of calls

⚠
Unauthenticated Webhook Endpoint
Anyone who finds your URL can POST fake call events and drain your credits
▼
⚠The risk: Your /api/incoming-call endpoint is publicly accessible with no authentication. An attacker who discovers the URL can send fake IncomingCall events, causing your bot to answer phantom calls — costing you money, CPU, and API quota on every fake request.
Fix — Validate the Event Grid Secret
1
In your Event Grid subscription → Additional Features → add a Delivery property header: key = aeg-sas-key, value = a long random secret you generate.
↳ Why: Event Grid will include this header on every POST to your webhook. Only requests with the correct header are legitimate.
2
Store your secret as an App Service env var: WEBHOOK_SECRET=<your-random-string>.
3
Add this check at the top of your handler:
const secret = req.headers['aeg-sas-key']; if (secret !== process.env.WEBHOOK_SECRET) { return res.sendStatus(401); // Reject unknown callers immediately }
🔑
Connection String Exposure
A leaked ACS connection string lets attackers make calls billed to your account
▼
⚠The risk: If your ACS_CONNECTION_STRING is ever accidentally logged, committed to Git, or exposed in an error, attackers can use it to place outbound calls, read call metadata, and run up a large bill — all authenticated as you.
Fix — Use Azure Key Vault + Managed Identity
1
Create an Azure Key Vault resource in rg-voice-bot. Store your connection string as a secret inside it.
↳ Why Key Vault: Secrets are encrypted at rest, access is audited, and you can rotate them without changing your code or redeploying.
2
Enable Managed Identity on your App Service: App Service → Identity → System assigned → On.
↳ Why Managed Identity: Your app gets an Azure AD identity and can read Key Vault secrets automatically — no password or connection string in your App Settings at all.
3
In App Settings, replace the raw connection string with a Key Vault reference: @Microsoft.KeyVault(SecretUri=https://your-vault.vault.azure.net/secrets/ACSConnectionString/)
💡As an immediate quick fix before setting up Key Vault: make sure your .env file is in .gitignore and never pushed to GitHub.
🛡
No Rate Limiting — DoS Risk
A flood of fake requests can exhaust your server and block real calls
▼
⚠The risk: Without rate limiting, a single attacker (or a misconfigured client) can fire thousands of requests per second at your webhook, saturating your App Service CPU and memory — making your bot unresponsive to real incoming calls.
Fix — Add Rate Limiting Middleware
1
Install: npm install express-rate-limit
2
Add to your server:
const rateLimit = require('express-rate-limit'); app.use('/api/', rateLimit({ windowMs: 60 * 1000, // 1 minute window max: 100, // max 100 requests per IP per minute message: 'Too many requests' }));
💡For production, also add Azure API Management (APIM) in front of your App Service — it provides enterprise-grade rate limiting, IP allowlisting, and usage analytics at the gateway level.
🎙
Audio Data Privacy (PII / GDPR)
Every caller's voice is PII — it must be handled with legal care
▼
⚠The risk: The PCM audio of every caller flows through your server and into your AI pipeline. Voice data is legally classified as Personally Identifiable Information (PII) in GDPR (EU), CCPA (California), and HIPAA (healthcare). Mishandling it can result in large fines.
1
Do not log or store raw audio unless you have explicit user consent and a documented retention/deletion policy.
↳ Storing even 10 seconds of audio per call at 1,000 calls/day = gigabytes of legally sensitive data that must be encrypted, access-controlled, and eventually deleted.
2
If storing transcripts: encrypt at rest (Azure Storage Service Encryption is on by default) and set an automatic deletion policy (e.g., delete after 30 days).
3
Play a consent recording at the start of every call: "This call may be processed by AI. Press 1 to continue or hang up to decline."
↳ This is legally required in many jurisdictions and provides a documented consent event.
4
Check whether your STT/LLM providers (Google, OpenAI, etc.) use your data to train models. Opt out or use enterprise tiers with data processing agreements (DPAs) if required.
🔌
Unauthenticated WebSocket Connections
Any client can open a socket to your audio endpoint without proving it's ACS
▼
⚠The risk: Your wss://yourserver.com/audio endpoint has no token check. Anyone can open a WebSocket to it and either inject fake audio or consume server resources by holding idle connections open.
1
When your webhook answers a call, store the callConnectionId in a short-lived cache (Redis or in-memory Map with a TTL).
↳ When ACS connects to your WebSocket, it sends a metadata frame with this ID. Only IDs you recognise are real ACS connections.
2
On WebSocket connection, read the first message frame, extract callConnectionId, and validate it exists in your cache. Close the socket immediately if not found.
3
Remove the ID from cache once the WebSocket closes to prevent reuse.
📈
Scalability — The Core Problem
Why a single App Service collapses under thousands of concurrent calls
▼
⚠The hard wall: Each active call holds one persistent WebSocket connection to your server. At 1,000 concurrent calls that's 1,000 open sockets + ~128 MB/s of continuous PCM audio data + 1,000 simultaneous STT/LLM/TTS API requests. A single App Service B1 instance (1 core, 1.75 GB RAM) will collapse well before 100 concurrent calls.
Why WebSockets are Hard to Scale
①
Stateful connections: Unlike HTTP, a WebSocket stays open for the entire duration of a call (minutes). The exact same server instance must handle all packets for that call — you can't round-robin them to different servers mid-call.
↳ This is called the "sticky session" problem. Standard load balancers break it unless configured specifically for WebSocket affinity.
②
Memory per connection: Each WebSocket connection holds input/output buffers, a PCM audio buffer, STT client state, and LLM conversation history. At 1,000 calls this easily exceeds 4–8 GB RAM.
↳ Every dropped connection = a dropped call. The caller hears silence and the AI goes unresponsive.
③
API rate limits: STT, LLM, and TTS providers enforce concurrent request limits. At 1,000 calls you'll hit these limits within seconds — calls will queue, latency spikes, and callers hear unnatural pauses.

Production-Scale Architecture
How to redesign for thousands of simultaneous calls using Azure-native services
▼
💡Key principle: Split the stateless webhook receiver from the stateful audio workers. Connect them with a message queue so a traffic spike can't crash either layer.
Step 1 — Decouple Webhook from Audio Processing
1
Your webhook (/api/incoming-call) should only: validate the event, answer the call via SDK, push a job to Azure Service Bus, and return 200 immediately.
↳ This makes the webhook stateless. It can scale to hundreds of instances behind a load balancer with no WebSocket affinity concerns.
2
Deploy Audio Worker Pods (Container Apps or AKS pods) that each pick one job from Service Bus and own that call's WebSocket + STT + LLM + TTS pipeline until the call ends.
↳ Each pod handles exactly one call. You scale the number of pods to match the number of concurrent calls. No sticky session problem.
Step 2 — Auto-Scale Audio Workers
3
Configure KEDA (Kubernetes Event-Driven Autoscaler) on AKS — or Container Apps' built-in scaling rules — to scale worker pod count based on the Service Bus queue depth.
↳ When 500 calls come in simultaneously, 500 pods spin up automatically. When calls end, pods scale back to zero. You only pay for what you use.
Step 3 — Handle API Rate Limits
4
Use multiple API keys (across different accounts or projects) rotated via a pool, or self-host open-source models:
• STT: Faster-Whisper running on GPU VMs (no per-request cost)
• LLM: Azure OpenAI with provisioned throughput (predictable capacity)
• TTS: Azure Neural TTS with dedicated capacity tiers
